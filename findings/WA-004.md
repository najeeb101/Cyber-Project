# WA-004 - Finding Record

**Status:** Verified (manual), remediation and retest pending
**Title:** Broken object-level access control (IDOR) on `/rest/basket/:id`
**Affected URL/component:** `http://127.0.0.1:3000/rest/basket/:id`
**Technical owner:** Member 3
**Risk reviewer:** Member 4

## Preconditions

A valid session (JWT) for any authenticated user. No elevated privileges required.

## Discovery and reproduction

**Discovery method:** Manual testing per `test-case-matrix.md` TC-002, using two synthetic accounts created for this test.

1. Register two synthetic accounts, `synth.a@lab.test` and `synth.b@lab.test`, via `POST /api/Users/`.
2. Log in as each account via `POST /rest/user/login` and note each account's own basket id (`bid`) returned in the `authentication` object (A: id 25 / basket 6, B: id 26 / basket 7).
3. While authenticated as B (holding B's own valid JWT), request `GET /rest/basket/6` — the basket id belonging to A — by substituting the identifier in the URL.
4. Observe the HTTP status and response body.

## Expected behavior

Per `test-case-matrix.md` TC-002, the server should reject access to an object the authenticated user does not own (403 or empty response), regardless of the identifier supplied in the URL.

## Observed behavior

The server returned HTTP 200 and the full basket object belonging to user A (`"UserId":25`) in response to a request authenticated as user B (`"UserId":26`). The endpoint authenticates the caller (a request with no/invalid token is rejected with 401) but does not authorize the caller against the specific basket id requested. Both test baskets were empty, so no synthetic order contents were exposed beyond basket existence and ownership metadata.

## Analysis

- OWASP category: A01:2025 Broken Access Control (Insecure Direct Object Reference)
- Confidentiality impact: Medium to High. Any authenticated user can read another user's basket (products, coupon) by guessing or incrementing a small integer id; the same pattern likely extends to basket updates/deletes (not tested here — see Limitations).
- Integrity impact: Not directly tested; the same missing ownership check pattern on write endpoints (e.g. adding/removing basket items) would allow tampering with another user's basket if present.
- Availability impact: None observed.
- CVSS-informed severity: Medium to High. CVSS v3.1 base 6.5 (Medium): `CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N` for the read-only path confirmed here; qualitative risk High (any registered user can exploit it). Reasoning: `report/risk-register-and-cvss.md` §3.
- Confidence and limitations: High that the read path is exposed, confirmed by direct reproduction with two independently created synthetic accounts. Only `GET /rest/basket/:id` was tested; write operations on another user's basket and other object types (e.g. orders) were not tested and are not claimed as confirmed. Basket ids were low sequential integers in this fresh lab instance, making enumeration trivial.

## Remediation and retest

**Recommended remediation:** On every basket (and similar per-user object) endpoint, verify server-side that the basket id in the request belongs to the authenticated user's own account (compare against `UserId`/`bid` from the verified JWT) before returning or modifying data; return 403 on mismatch instead of the object.
**Retest result:** Pending. Planned: apply the ownership check and repeat steps 3-4 above, expecting 403.
